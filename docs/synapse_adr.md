# Synapse プラグイン ABI — Architecture Decision Record (ADR)

`synapse_abi.h` の背後にある設計判断・今後のロードマップ・未解決の論点を記録する。
ヘッダは「何がそうなっているか」を、本 ADR は「なぜそう決めたか／何を却下したか／何が未決か」を保持する。

- 対象: ノードベース映像合成/編集フレームワーク "Synapse" のプラグイン C ABI
- 状態の凡例: **Accepted**（確定） / **Accepted (v1暫定)**（最小実装では確定、後で差し替え予定） / **Deferred**（方針は決定、実装/詳細は先送り） / **Open**（未決）
- 各 ADR テンプレート: 文脈 / 決定 / 却下案 / 帰結

---

## 1. 決定記録 (Decisions)

### ADR-001: Pull型・スタック駆動・非再帰評価器
**状態**: Accepted
**文脈**: 遅延評価・ホットリロード・キャンセル・並列スケジューリング・FFI 安全性を同時に満たす必要がある。
**決定**: ホスト駆動の pull 型、スタックベース非再帰評価器（Blender 第3世代 lazy-function graph に着想）。
**却下案**: (1) 再帰 FFI 評価 — ホスト状態の再入・ホットリロード・キャンセル/タイムアウト・並列スケジューリング・言語跨ぎランタイムを壊す（スタック深度だけなら stacker で対処可だが他は不可）。(2) ECS — pull 型グラフ評価に不適合（UI/エディタ側には向く）。
**帰結**: FFI が再帰しない。後述の「同一インスタンス直列化」(ADR-019) が自然に成立。

### ADR-002: 宣言/処理の2フェーズモデル
**状態**: Accepted
**文脈**: 再入を問題クラスごと消したい。依存/フレーム交渉とピクセル処理を分離したい。
**決定**: `declare`（ピクセルデータ無し：依存/フレーム交渉）+ `process`（要求されたバッファのみ受領）。
**却下案**: 単一の処理関数内で依存解決とデータ処理を混在させる（再入と責務集中を招く）。
**帰結**: 再入が構造的に発生しない。領域/フレーム交渉は宣言クラスの関数に置く。

### ADR-003: 純粋 C ABI 境界（FFI 安全性をハード制約に）
**状態**: Accepted
**文脈**: 言語非依存・安定した境界が要る。プラグインを AI/コミュニティに委譲できる小さな契約面。
**決定**: 単一エントリポイント（`synapse_module`）、不透明ハンドル、スイートによる機能提供（OFX 由来パターン）。
**却下案**: C++ ABI（不安定）/ 言語固有 ABI（委譲不能）。
**帰結**: OFX の単一エントリ/プロパティ集合/スイート版数の発想を採るが、画像エフェクト中心モデルと外部ガバナンスは継承しない。

### ADR-004: プラグイン2種別（型パッケージ / 処理プラグイン）、ホストはデータ意味論に不可知
**状態**: Accepted
**文脈**: データの意味をホストに焼き込むと、ベンダー間で侵食・硬直する。
**決定**: `register_type`（データ宣言・メモリ配置・vtable）と `register_node`（ノードロジック）の2側面。ホストは中身を解釈しない。
**却下案**: ホストが全型を理解する設計 / データに vtable を添付する "Level 2" 方式（データ宣言と振る舞いの分離を破る）。メタデータは独立した型付きエッジを流れる前提で、Level 2 を捨て canonical 型 + 変換ノードを基線とした。
**帰結**: 「インターフェース実装」も単なる処理プラグインに収まる。

### ADR-005: URID による型同定、ワイヤは {URID, ptr, size}（vtable ポインタを載せない）
**状態**: Accepted
**文脈**: vtable はプロセスローカルでホットリロードに伴い揮発する。IPC/永続化に耐える同定子が要る。
**決定**: URID（LV2 流）。セッション安定の整数で型を同定。vtable は lookup で引き、init 時に取得してセッション中キャッシュ（主流プラグイン API の慣行）。
**却下案**: fat pointer / vtable をワイヤに載せる（プロセスローカル・再ロードで揮発）。型 URI 文字列をワイヤに載せる（冗長・コスト）。生ポインタをワイヤに載せる（クロスプロセス互換を破る；相対オフセット方式も検討したが URID に集約）。
**帰結**: 永続化・プロセス越えが将来可能。PLAIN payload は「位置独立な素のバイト列・生ポインタ非内包」が不変条件 (ADR-006)。

### ADR-006: データ単位の SVO（8byte 以下インライン格納）
**状態**: Accepted
**文脈**: スカラが大量に流れるサブグラフで、小さい値ごとのヒープ往復・局所性・寿命管理が問題になる。
**決定**: `size <= sizeof(void*)` の値は `ptr` フィールドにビット格納（SVO）。読み書きは memcpy 経由（ストリクトエイリアシング回避）。
**却下案**: 小さい値も常にヒープ確保しポインタ参照（確保/解放のコスト、キャッシュミス、寿命管理が増える）。
**帰結**: 得は命令速度ではなく「確保ゼロ・局所性・寿命=SynValue 寿命」。payload に生ポインタを入れない不変条件と整合。空判定は ADR-018 へ。

### ADR-007: 出力型は1つ固定 / 入力は多態 / 型交渉は接続時のみ
**状態**: Accepted
**文脈（決定的）**: プロデューサ側で結果をマテリアライズ&キャッシュするため、生産/消費に非対称がある。出力型を固定するとキャッシュキーから「要求された型」が消え `(node, params, frame, region)` に縮み、fan-out のキャッシュ断片化を防げる。出力側多態は、プロデューサのキャッシュ前提がコードベースに伝播すると後戻り不能になる。
**決定**: 出力ソケットはちょうど1型。入力は受理型集合（多態）。型交渉はソケット接続の瞬間のみ。
**却下案**: 上流優先マッチ / 下流優先マッチ / 入力側固定 / 両側多態。
**帰結**: 汎用ノードの出力型は別途解決が要る (ADR-013)。消費側多態（受理型リスト）とホスト側型変換（convert ノード）は互いに直交で、ABI を変えず後付け可能。

### ADR-008: multi-input（fan-in）= 1宣言ポートで N リンク受理。データ構造の多重度とは直交
**状態**: Accepted
**文脈**: 可変入力で「途中挿入でリンクがずれる」を避けたい。
**決定**: 1つの安定宣言ポートが複数リンクを受け、評価時に順序付きハンドル配列を配送（Blender 流）。
**却下案**: 番号付きスロット（序数同定が並べ替えに脆い：Nuke/OFX general context）/ request-pad の重い命名・寿命契約（GStreamer）/ multi-input と list・field の多重度を ABI で混同すること。
**帰結**: 多重度（トポロジ）とカードナリティ（list/field）は別軸として扱う。

### ADR-009: 可変出力は単一ポートの `List<T>` + 抽出ノード（トポロジにしない）
**状態**: Accepted
**文脈**: 可変な出力ポート数は pull 評価と構造的に相性が悪い。
**決定**: 単一出力ポートが `List<T>` を運び、下流の get-item/separate ノードが取り出す。
**却下案**: 出力ポート数自体を可変にする（トポロジ ABI の問題化）。
**帰結**: 可変入力(ADR-008)と可変出力で別機構。後者は ABI のトポロジ問題にならない。

### ADR-010: Blender 流の冪等宣言、安定 key で reconcile
**状態**: Accepted
**文脈**: 状態遷移ごとの特殊ケースを消したい。可変ソケットのリンク・既定値を壊さず保持したい。
**決定**: `declare` はインスタンス状態から毎回フルのソケット一覧を再生成。ホストが安定 key（序数 index ではない）でリンクと既定値を突合・生成・削除・並べ替え。
**却下案**: init 関数方式の逐次ソケット改変（特殊ケースが増えエラーが起きやすい）/ 序数同定（並べ替えに脆い）。
**帰結**: index は1回の declare 内のみ安定、key は再 declare を跨いで安定。既定値も key で reconcile（既存 key は編集値を維持、初期既定値は新規 key にのみ適用）。C ABI 越えでは Blender の「毎回全再構築の安さ」をそのまま移植できない点が差分。

### ADR-011: negotiate はデータ無し・単発（クリーン2パス）
**状態**: Accepted
**文脈**: 型交渉は接続時のみ。ここでの「動的依存」はグラフ依存ではなくデータ依存の意。negotiate がデータを読まないなら、要求集合は `(状態, 下流要求)` の純関数で1回呼べば確定する。
**決定**: negotiate は必要入力を1回列挙して返す。process は全充足後に1回。
**却下案**: NEED_INPUTS/READY による反復 poll と negotiate 内でのデータ読み（値依存の遅延枝刈りにのみ必要 → 二層 API へ先送り ADR/Open 参照）。
**帰結**: 静的ノードは全入力を列挙するだけの縮退形。値依存枝刈りを入れる段でそのノードに限り反復 poll が再導入される。

### ADR-012: プラグインは FFI を跨ぐメモリを確保しない。跨ぐ側は必ずホスト管理
**状態**: Accepted
**文脈**: 所有権が FFI を越えると安全に管理できない。
**決定**: 宣言はホストのビルダ callback、要求はホストの request callback、出力は `alloc_output` でホストが確保しプラグインが書く。プラグイン私有メモリ（UI 状態等）は確保/解放がともにプラグイン側で所有権が FFI を跨がない限り自由。
**却下案**: プラグインがヒープ確保した配列/値を返す（所有権が FFI を越え不安全）。
**帰結**: ABI 表面に「プラグインが確保して返す」経路が存在しない。

### ADR-013: 汎用ノードの出力型解決 — v1 は ANY(方式a)、目標は型伝播(方式b)
**状態**: Accepted (v1暫定)
**文脈**: ADR-007 で出力型固定としたため、reroute/switch/`List<T>`抽出 のような出力型が入力従属のノードに別解が要る。
**決定**: v1 は出力を `SYN_TYPE_ANY` で宣言し process 時に実体型を解決。`connected_type` を ABI に追加済みで、方式b への移行は「恒等伝播ノードはホスト内部の型伝播でプラグイン無改修」「派生型ノードのみ declare で connected_type を使う」に分かれ、ABI 変更を伴わない。
**却下案**: v1 から完全な方式b（ホストのトポロジカル再 declare 伝播パスが必要で最小実装には重い）。
**帰結**: 唯一まとめて先送りされるのは「接続型変化を declare 無効化トリガとしトポロジカル順に再宣言を伝播する」ホスト内部パス。

### ADR-014: キャッシュは dirty 伝播で無効化（キーに状態/データを入れない）
**状態**: Accepted
**文脈**: データバッファを毎回ハッシュするのは量に比例した無駄で、DAG では不要。
**決定**: キャッシュキー = `(frame [, 将来は下流リクエスト])`。状態変更時に当該ノード + 下流サブツリーを再帰的に無効化。プラグインは内部不透明状態の変更時のみ `mark_dirty` を呼ぶ。ソケット既定値の編集はホストが直接検知して無効化。
**却下案**: データのハッシュをキーにする（高コスト・冗長）/ ノード状態のハッシュをキーに含める（無効化方式を選択）。
**帰結**: 成立条件＝「状態変更は下流サブツリー全体を無効化」（load-bearing 不変条件）。no-op 編集でもキャッシュは飛ぶ（受容するトレードオフ）。出力型固定(ADR-007)とも整合。

### ADR-015: SHARED/OPAQUE の clone は浅いコピー（clone/drop は refcount の対）
**状態**: Accepted
**文脈**: passthrough で GPU/大容量リソースを複製すると実コピーが走る。
**決定**: PLAIN/可変型は deep copy。SHARED/OPAQUE は clone=refcount++、drop=refcount--（0 で実リソース解放）。
**却下案**: 全型 deep copy 固定。
**帰結**: passthrough と reroute がリソースを複製しない。

### ADR-016: 型+API 二層（エスケープハッチ）
**状態**: Accepted
**文脈**: GPU リソース等はそのままバイナリ化できない。
**決定**: OPAQUE 型は不透明ハンドルを持ち、`vtable.get_api(api_id)` で自前 API テーブルを公開。ホストは中身を解釈せず、寿命のみ clone/drop で管理。
**却下案**: 全型をシリアライズ可能バイト列に強制（GPU では不可能）/ データにvtableを添付する Level 2（ADR-004/005 で却下）。
**帰結**: 基本はバイナリ読み書き、不可能なものだけ API 経由のエスケープハッチ。

### ADR-017: パラメータ/永続化モデル（Blender 流・3層）
**状態**: Accepted
**文脈**: パラメータがプラグイン私有だと、永続化・オートメーション・汎用 UI・UI/処理の並行が後で困難（OFX/VST3/CLAP/LV2 はいずれもホスト可視）。
**決定**: ソケット既定値 = パラメータ（ホスト所有）。型が default(init/値)+serialize を備えれば、ホストが意味を理解せずとも保存・配送できる。3層: **Tier A**（canonical 型：汎用編集 UI + 既定値 + 永続 + 将来の自動化）/ **Tier B**（登録済みカスタム型で serialize+init：保存・配送可、汎用 UI 無し）/ **Tier C**（serialize/既定値なし：接続必須）。ソケットに出ない内部パラメータは `save_state`/`load_state` の不透明 blob。
**却下案**: パラメータ私有（上記の4機能を失う）/「blob にソケット既定値を入れない」を明文ルールにする（構造的に解決：プラグインは get_input の借用しか持たず既定値の getter も無いので blob に入り得ない）。
**帰結**: 自動化対象はソケット既定値のみ（内部 blob は不可）→「アニメーションさせたい値はソケットに出す」が指針。mark_dirty が要るのは内部状態変更時のみ。

### ADR-018: 空値 sentinel は `type_id==0`（`ptr==NULL` は使わない）
**状態**: Accepted
**文脈**: 既定値も接続も無いソケットを表現したい。SVO により `ptr` フィールドは値と兼用。
**決定**: 既定値の無い未接続入力は `type_id==0`（空）を配送。プラグインが処理を一任（空出力 or 内部フォールバック）。`syn_is_empty` ヘルパ。
**却下案**: `ptr==NULL` を空とする（SVO の inline 零値 float 0.0 / int 0 と区別不能）/ ホストが接続必須を強制（optional-everywhere を採用、required フラグは後付け可能）。
**帰結**: 空はグラフを自然に伝播。optional 入力の読み出しは必ず空チェックする規律。

### ADR-019: 呼び出し直列化を既定、UI 並行は opt-in
**状態**: Accepted
**文脈**: 同一インスタンスの状態を process と UI が同時に触ると競合する。
**決定**: 同一インスタンスへの全エントリ呼び出しは重ならない（スレッドは跨いでよい）→ プラグインは同期不要。異インスタンス間の並列は可。UI と process の同一インスタンス並行は `SYN_CAP_THREAD_SAFE_UI` を立てた時のみ許可。
**却下案**: グローバル直列化（粗すぎ）/ 共有可変状態 + ロックを既定にする。
**帰結**: 将来は CLAP/OFX 流（関数ごとのスレッド注釈 / レンダのスレッド安全性宣言）に寄せる。UI 並行を本気でやる段ではホスト仲介のパラメータチャネルが自然。ADR-001 の「FFI 再帰なし」と同じコインの裏表。

### ADR-020: バージョニングは当面先送り
**状態**: Deferred
**文脈**: クローズドな単独開発の間は API 安定性を求めない。
**決定**: `struct_size`/版数引数の儀式を撤去し `SYN_ABI_VERSION` 一個に。スイートは id で取得、構造体は版内で固定。
**却下案**: 完全な前方互換機構（時期尚早）。
**帰結**: 規格化に入る段で OFX 流スイート版数 + append-only/拡張クエリ（CLAP 流 get_extension）を再導入する。

### ADR-021: 並列軸の v1 スコープ
**状態**: Accepted（軸1,3）/ Deferred（軸2,4）
**文脈**: 並列はインスタンス再入を要する軸とそうでない軸がある。
**決定**: v1 は軸1（クロスノードのタスク並列）と軸3（スレッドスイートによるプラグイン内並列）を対象。軸2（インスタンス再入タイリング）・軸4（フレーム並列）は今は caps フラグの宣言のみ、実装は後。
**却下案**: 全軸を v1 で実装。
**帰結**: 「直列が保守的既定、並列は宣言制 opt-in」。

### ADR-022: 評価境界の SynValue は値渡し（参照は ptr を通してのみ）
**状態**: Accepted
**文脈**: 当初 `get_input`/`alloc_output` は `out_value: *mut SynValue` の out パラメータ方式だった。最小ホスト実装（M0）で、`alloc_output` が埋める out パラメータはプラグインのローカルなので、プラグインが SVO 値（≤8byte のインライン）を書き戻してもホストから見えない、という非対称が判明した（FINDINGS F-1）。
**決定**: `SynValue` は境界を**値渡し**で越える。`get_input(ctx,in,link) -> SynValue`（値返し）、`set_output(ctx,out,value: SynValue)`（値渡し）。大型(>8byte)出力はホスト確保プリミティブ `alloc(ctx,size) -> *mut c_void` でバッファを得て書き、その ptr を `SynValue.ptr` に入れて set_output する。`passthrough`・`input_default` も値渡しに統一。参照は SynValue 内の `ptr` を通してのみ行う。
**却下案**: out パラメータ + ホスト所有バッファへの write-through（SVO で読み書き非対称になる）/ `commit_output` を別途足す（ABI 表面+1で、値渡しの方が単純）/ `*const SynValue` 渡し（呼び出し中コピーで等価だが、設計者の「値渡し」意図に劣る）。
**帰結**: SVO のビットが構造体ごとコピーされ、プラグインローカル不可視の問題が原理的に消える。読み出しと書き込みが対称になり SDK の隠蔽負担が減る。確保はホスト（ADR-012）を維持。

### ADR-023: 1プロセス=1ホスト=1セッション（ctx 無しスイートはプロセスグローバルが正、ABI 変更不要）
**状態**: Accepted
**文脈**: 最小ホスト実装（M0）で2点が浮上した（FINDINGS F-2/F-3）。(1) `SynUridSuite::map/unmap` と `SynTypeRegistrySuite::register_type/lookup/type_of` はハンドル引数を一切取らないため、C の関数ポインタはデータを閉じ込められない（クロージャではない）以上、**その背後の状態は構造的にプロセスグローバル（または thread_local）にしか置けない**。ホストをヒープに置いて `Box::leak` 等で渡す手法は、第一引数に `h: *mut SynHostStruct` を受け取るコールバック（`register_node`/`mark_dirty`/`log` 等。`h->host_ctx` 経由で状態に辿れる）には有効だが、引数にハンドルが無いこれらのスイート関数には適用できない。(2) declare/negotiate/process はスイートポインタを引数で受け取らないため、プラグインは on_load で fetch したスイートをモジュールグローバルに保持する必要がある。
**決定**: マルチホストを想定しない。同一プロジェクトファイルに複数ホストを立てるとデータの SSoT 性に疑念が生じるため、**1プロセス=1ホスト=1セッション**を不変条件とする。この前提下ではプロセスグローバルこそが「セッション」の実体であり、ADR-005 の「URID はセッション安定」と整合する。プラグイン側のスイート保持も「1モジュール=1ホスト」（ハンドシェイク=on_load で確定）の前提で正当であり、ボイラープレートは SDK 層が隠蔽する。**いずれも ABI 変更は行わない。**
**却下案**: urid/type-registry スイートにも `h` を足す（マルチホストを想定しないため不要。将来必要になれば追加は機械的）/ declare/process にスイートを引数で渡す（シグネチャが太る。CLAP 同様「on_load で渡しプラグインが保持」が定石）。
**帰結**: テスト分離はプロセスグローバル共有のままで実害が小さい（URID intern は単調追加で、テスト間共有は「ID 値が実行ごとに変わる」だけで意味論は壊れない。型レジストリの衝突が問題になるテストは URI の名前空間分けか統合テストバイナリの分離=プロセス分離で対処）。将来マルチホストが必要になった場合は、ハンドル無しスイート関数への `h` 追加という ABI 変更が必要になる——本 ADR がその判断の参照点。

### ADR-024: コールバック境界の unwind は abort、エラーは戻り値（`extern "C-unwind"` 不採用）
**状態**: Accepted
**文脈**: 関数ポインタはすべて `extern "C"`。境界を越える巻き戻し（Rust panic / C++ 例外）は未定義ではなく abort になる。プラグインの不正やバグでホストプロセス全体が落ちるのは堅牢性方針に反する。
**決定**: 「ABI は C・エラーは戻り値（`SynStatus`/空値）」を規律とする。**両側の実装**は自分の `extern "C"` コールバック内で巻き戻しを必ず捕捉する。プラグイン側 SDK は `catch_unwind`→`SYN_ERR_UNKNOWN`、ホスト側境界層も全コールバックを `catch_unwind` で包み、`SynStatus` 返しは `SYN_ERR_UNKNOWN`、値返しは安全なデフォルト（空 `SynValue`/`0`/NULL）に落とす。関数ポインタ型は `Option<unsafe extern "C" fn ...>`（NULL 可能性＝`Option`、未検証ポインタ＝`unsafe` を型で表す）。ポインタ引数は明記なき限り非 NULL、信頼境界（プラグイン→ホスト）の実装は防御的に NULL 検査して `SYN_ERR_BAD_ARG` を返してよい。
**却下案**: `extern "C-unwind"` で巻き戻しを越境させる（メリットは「C++ 例外の素通し」「Rust↔Rust の panic 伝播」だが、言語非依存性と『エラーは戻り値』の規律を弱める。需要が出るまで不採用）。
**帰結**: 巻き戻しはプロセスを落とさず必ず `SYN_ERR_*`/安全値に変換される。境界規約はヘッダ冒頭の散文にも明記。

### ADR-025: アンロード安全性 — 記述子はモジュールイメージ内 static + アンロード時グローバル purge
**状態**: Accepted (v1暫定)
**文脈**: ノード記述子（`SynNodeDesc`）と型 vtable（`SynTypeVTable`）のポインタはプロセスグローバル（型レジストリ／ノード登録, ADR-023）に積まれる。これらを `Box::leak`（ヒープ）で確保するとアンロード（dlclose）後もヒープに残ってリークし、かつグローバルに残った生ポインタは dlclose で無効化されたコードページを指して dangling になる。
**決定**: (1) 記述子/vtable は **モジュールイメージ内の static**（SDK は型/ノードごとの関連 `const` を `&` で 'static 参照に昇格、モジュール記述子はマクロ内 `static`）に置く——リークせず、dlclose でイメージごと正しく解放される。(2) ロードごとに `ModuleId` を採番して登録の出所を追跡し、**アンロード時（および on_load 失敗時）に当該モジュールの登録をグローバルから除去（purge）** する。purge はアンロード時のみ走り、**ホットパスはゼロコスト**。PLAIN 型の値はバイト列でプラグインに依存しない（drop 不要・vtable をデータに載せない, ADR-005）ため、v0.1（PLAIN のみ）はこの purge だけでアンロードが健全になる。
**却下案**: (a) 全データを参照カウントで監視し完全 drop までアンロード遅延（PLAIN にも atomic コストが乗る・ホットパス非ゼロ）。(b) vtable 解決のたびに map 存在確認（opaque 操作ごとに lookup コスト）。(c) この lifetime 管理を unsafe でホスト本体に丸投げ（安全境界層の存在意義に反し unsafe が上位に増殖する）。
**帰結**: v0.1 はゼロコストでアンロード健全。**将来 OPAQUE/SHARED 型を入れる段**では、その型の値だけが `Arc<ModuleToken>` 相当を抱きアンロードを遅延する「opaque 値限定 RC」を安全層に追加する（PLAIN は引き続きゼロコスト。OPAQUE は GPU/大リソースのラッパで元々重いので atomic 1 回は誤差）。さらに将来は型・バイナリ・ノードの依存追跡による一括処理へ移行する余地を残す（ADR は移行の参照点。Open-12 参照）。

### ADR-026: 評価境界の値受け渡しと寿命（出力=ホスト確保／入力=借用、32-bit でも SVO 分岐）
**状態**: Accepted
**文脈**: ADR-022 で `SynValue` は値渡し、SVO（≤ポインタ幅）はインライン・大型は `ptr` 経由と決めた。SDK の値変換が「≤8byte 前提（`debug_assert`）」だったため、32-bit（ポインタ幅 4）で 8byte 型（f64/i64/u64）が release ビルドでスタックを壊す不具合があった。また「大型値の所有権と寿命」は出力と既定値で異なる。
**決定**: 値の出し入れは `size <= sizeof(void*)` の **const 分岐**で SVO/領域を出し分ける（64-bit の常用型では分岐ごと消えゼロコスト、32-bit では 8byte 型が領域経路に乗り正しく動く）。寿命契約は用途で非対称:
- **出力（set_output）**: 出力値は下流に伝播しホストが保持する。**大型は必ずホスト確保バッファ（`alloc`, ADR-012）に書いてその ptr を渡す**。
- **既定値（input_default）**: ホストが呼び出し中に型 vtable で clone する。**大型は呼び出し中のみ有効な借用（プラグインのフレームに生存する値への参照）でよい**。
- **入力読み出し（get_input）**: ホスト所有領域の借用で受け取り、その呼び出し中のみ有効。
**load-bearing 前提**: 入力を借用で扱える健全性は「**プロデューサ（出力ノード）が結果をキャッシュ＝データを所有する**」ことに依る（ADR-007/014）。将来データ所有権をグラフに流すモデルへ変える場合、入力も出力と同じ「ホスト確保＝所有移転」扱いに変える必要がある。
**却下案**: 8byte 型を 32-bit でコンパイルエラーにして締め出す（型レベルで安全だが「64-bit 専用 ABI」に縮む。const 分岐で両対応できるため不要）。SDK 読み出しで型/サイズ未検証のまま memcpy（ANY 宣言・上流バグで異型が届くと範囲外読み＝UB。`InPort` に declare 解決済み URID を埋め `type_id`+サイズを照合し不一致は `None`/`Err(TypeMismatch)` に倒す）。
**帰結**: `SynPlainType` の健全性条件は「`SIZE == size_of`」のみ（≤8byte 制約は撤廃）。post-mono アサートで `SIZE` 不一致をコンパイル時に弾く。

## 2. ロードマップ (Roadmap)

順序は目安。基盤的決定（ABI/ワイヤ：v1 で正しくある必要）と追加的決定（後で層を重ねられる）を区別している。

- **M0（現在）— 最小ホストが動く**: このヘッダ、URID/型レジストリ/decl/eval スイート、scalar 型パッケージ、scalar 加算ノード（declare→negotiate→process と save_state の通し確認）。グラフはインメモリ。
- **M1 — パラメータと保存**: canonical 型集合の確定 (Open-10)、Tier A の汎用パラメータ UI、プロジェクト永続化（ホスト既定値 + save_state）、dirty 伝播キャッシュの実装。
- **M2 — 画像と GPU**: 画像型、GPU エスケープハッチ（OPAQUE + get_api, ADR-016）、passthrough、multi-input、`List<T>` + 抽出ノード。
- **M3 — 型と領域**: 方式b への型伝播 (ADR-013)、ホスト側 convert ノード自動挿入 (Open-9)、ROI/領域交渉（下流→上流, Open-7）。
- **M4 — 二層 SDK と並列**: 簡易 eager + 再開可能 lazy（async/await で状態機械隠蔽, Open-8）、並列軸2/4 (ADR-021)、キャンセル/進捗 (Open-6)。
- **M5 — 増分と高度化**: Salsa 風インクリメンタル層 (Open-4)、field 意味論 (Open-3)、ホットリロードの堅牢化 (Open-12)、規格化に向けたバージョニング (ADR-020)。

## 3. 未解決の設計判断 (Open Questions)

実装着手前/着手中に決める必要があるもの。残さず記録する。

- **Open-1: multi-input のグループ型統一**: 接続時に caps 交渉で受理型の統一を強制するか。未決。
- **Open-2: `List<T>` の評価責任と借用窓**: ホスト管理のメモリ借用窓が、multi-input ハンドル配列の寿命とどう相互作用するか。未決。
- **Open-3: field 意味論（Blender 軸IV）**: per-element の遅延値。Blender の menu switch で起きた組合せ爆発を避けるため意図的に延期。未設計。
- **Open-4: Salsa 風インクリメンタル計算層**: スタック評価器の上の第2層として計画。設計未着手。v1 ではやらない。
- **Open-5: カスタム UI 由来の既定値の受け渡し**: ホスト非対応型のソケットで、カスタム UI が動的に設定した既定値をホストへ戻す API。先送り（Tier B の init 由来固定既定値は追加 API 無しで保存可能なので、先送り範囲はこのケースに限定済み）。
- **Open-6: キャンセル/進捗**: 長尺レンダ用に process 内で polling する `should_cancel`。機構はスケッチ済み、未追加。
- **Open-7: 領域(ROI)の表現と交渉**: 領域は型と同様に扱い、ホストは意味を理解しない方針。下流→上流の伝播は v1 ではやらない。追加時の領域表現（不透明な型付き値 か 汎用 N 次元 extent か）は未決。
- **Open-8: 二層 SDK API の詳細**: 簡易 eager(~95%) と再開可能 lazy（条件分岐の枝刈り）。方向は確定、詳細設計は未。これが入ると negotiate (ADR-011) は該当ノードで反復 poll 化する。
- **Open-9: ホスト側型変換 / convert ノード自動挿入**: レジストリ駆動・プラグイン不可視。ADR-007 と直交で後付け可。未設計。
- **Open-10: canonical 型集合の確定**: Tier A の標準型。候補＝scalar(f64/i64/bool)/string/color(rgba)/vec(2/3)/mat4/image(rgba_f32 等)/audio(pcm_f32)/array(f32)/time(rational)/rect。確定していない。
- **Open-11: declare の key 表現**: 文字列 key か 整数 ID（ソケット ID/ノード ID）か。整数 ID 寄りだが未確定（寿命・比較コストの観点）。
- **Open-12: ホットリロードの機構**: 粗粒度フルリロード（全プラグイン同時）は方針決定済み。URID のリロード跨ぎ安定性、vtable 再解決、進行中呼び出しの扱いは未詳細化。アンロードの基盤は ADR-025（記述子の static 化 + ModuleId purge）で v0.1 から健全。残課題は (1) OPAQUE/SHARED 値が生きている間のアンロード遅延（opaque 値限定 RC）、(2) 型・プラグインバイナリ・ノードの依存を記録した一括（トランザクショナル）アンロード、(3) 進行中の declare/process とアンロードの排他。(1)→(2) の順で段階導入する想定。
- **Open-13: 規格化時のバージョニング方式**: ADR-020 で先送り。再導入時の具体（append-only/拡張クエリ/スイート版数の運用ルール）は未決。
- **Open-14: 可変長バッファのサイズ問い合わせ規約の統一**: save_state は `out=NULL/cap=0` で必要量を問い合わせる2段方式。型 vtable の serialize も同規約に揃えるか（現状コメント上は (out,cap,written) で同形）。確認事項。
- **Open-15: ホスト取り込み範囲のスコープ**: GPU 抽象 / メモリアロケータ / 色空間 / 時間 / bbox / 数値ユーティリティ / ファイル I/O / i18n / Undo・Redo / オーディオ基盤 など、どれをホストに取り込みどれをプラグインに委ねるか。型集合 (Open-10) を超える範囲は未決。
- **Open-16: multi-input のリンク順序**: コンポジタでは z 順になり、ユーザによる並べ替えが要る。ABI 的には `link_index` 順がホスト定義で評価中安定で足りるが、エディタ側の順序保持/並べ替え仕様は未定。
- **Open-17: 接続必須ソケットの強制**: 現状は optional-everywhere（空を流しプラグインに一任, ADR-018）。ホスト側で「必須」を強制する required フラグを入れるかは先送り。
- **Open-18: 生成ヘッダ（`synapse_abi.h`）の鮮度保証**: 正本は Rust（synapse-abi）で、`cargo build` の build.rs が cbindgen で `synapse_abi.h` を生成する（ヘッダはリポジトリにコミットして C 利用者へ配る成果物）。古いヘッダのコミットを防ぐため、CI で「再生成して `git diff --exit-code`」する運用に揃える（多くの Rust 製 C インターフェースの定石）。read-only / sandbox ビルドでソースディレクトリへ書き込めない問題はこの CI 運用で吸収する。CI 設定は未追加（リポジトリに CI が入った段で追加）。なお不透明ハンドル（SynNode 等）は Rust 側が PhantomData 構造体のため cbindgen が本体を出さず、前方 typedef を build.rs の after_includes で注入している（ADR-025 と関連）。

- **Open-19: `OwnedValue` の SVO ゼロアロケーション化**:
  `crates/synapse-host-abi/src/value.rs` の `OwnedValue` は、ABI 境界の SVO 最適化（ADR-006）をホスト内部の保管表現にまで引き継げていない。現状 `bytes: Vec<u8>` はサイズが ≤ポインタ幅の小型値（`bool`・`f32`・`i32` 等）であってもヒープ確保を行う。SVO の利点（「確保ゼロ・局所性・寿命 = SynValue 寿命」ADR-006）はプラグイン⇄ホスト間の**転送形式**（`SynValue`）にのみ効いており、`from_value()`/`to_value()` で変換した瞬間に失われる。また `#[derive(Clone)]` によるクローン毎にも同じアロケーションが発生する。
  **解決の方向性**: `OwnedValue` を専用クレート（例: `synapse-value`）に分離し、保管表現を `Inline([u8; PTR_SIZE])` と `Heap(Vec<u8>)` を出し分ける enum あるいは `SmallVec<[u8; PTR_SIZE]>` 相当の小バッファ最適化型に置き換える。`size <= PTR_SIZE` の経路では確保ゼロ・スタック局所となり ADR-006 の意図と一致する。ただし安全で正しい実装には `unsafe`（ユニオン操作・`Copy` 実装の手書き等）が伴うため、プロトタイプ段階での実施は非本質タスクとして先送りとする。

## 付録: 参照した先行技術と対応

OFX（単一エントリ/プロパティ集合/不透明ハンドル/スイート版数/レンダのスレッド安全性宣言）、
LV2（URID/DSP と UI の分離）、CLAP（関数ごとのスレッド注釈/拡張クエリ）、
Blender geometry nodes（冪等宣言/安定 identifier/multi-input/default_value 別ストレージ/単一 geometry ソケットでの型爆発回避）、
Nuke NDK（範囲ベース可変入力/uses_input）、GStreamer（pad presence 三分類）、
Halide・Salsa（増分計算）、Houdini を調査・抽出元としている。
本 ABI はこれらのパターンを「独立した設計軸に分解 → 軸ごとに選択 → 統合」する方針で構成した。
